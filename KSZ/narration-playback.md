# 讲解模式与播放进度

## 模式与篇幅

模型根据本轮意图和上下文判断模式，不需要用户固定说“详细”。导览触发、展区及展项介绍、主题解释、故事和继续讲解采用讲解模式，忽略角色和服务默认的一两句、字数、单段等短答限制；问候、设备控制、单个事实问题及明确要求简短时简答。每轮重新判断，用户指定的范围、时长和篇幅仍然有效，事实依据及绑定语言要求照常执行。

小智的策略在 `server/ksz_guide/prompt.py`，自动导览还会明确请求讲解；Museum Guide Agent 需同步更新四语 `ANSWER_LENGTH_PROMPTS` 和语言提醒，避免下游继续要求短答。仅改角色提示词不能解除两层服务的默认短答策略。

小智在 system 开头先声明角色中的字数、句数、段数只约束简答，再放入原有角色及本轮策略，避免模型继续服从靠前的“30字”等要求。角色身份、语言、语气及其余规则保留；重复生成系统提示和角色重绑不会重复添加篇幅策略。

`KSZ/.env` 的 `KSZ_NARRATION_MAX_TOKENS` 默认 `4096`，范围 `1–131072`，通过 LLM 请求的 `max_tokens` 传至兼容接口和 Agent。可按供应商允许范围提高；该项是生成预算，不是要求每次讲满。模型自身上下文/输出上限和设备每日使用额度仍有效。修改后重新创建 server 容器，不能只执行 `restart`。

## 打断后模型知道什么

服务端在按键 `abort`、未结束回复被新请求替代及连接关闭时记录打断；下一轮请求追加可信播放上下文，保留原始聊天历史。新问题优先回答，只有用户要求继续时才续讲。生成记录和回执仅保存在当前连接的内存中，最多六轮；重连不复用旧连接的播放状态。

| 字段 | 含义 |
| --- | --- |
| `confirmed_played_text` | 设备明确确认完整播完的段落 |
| `started_unconfirmed_text` | 服务端已发送对应 `sentence_start`，设备可能播放了部分，也可能尚未播，不能称为已听完 |
| `generated_not_started_text` | 已生成且还未发送对应段落开始的文本；字幕与生成文本无法按前缀对齐时为 `null`，不猜测未播部分 |
| `generated_text` | 当时已生成的文本，不能证明用户已听到 |
| `ungenerated_remainder` | 固定 `unknown`，尚未生成的后续内容无法预知 |
| `truncated` | 记录或本轮上下文摘要达到容量限制，不能视为完整全文 |

未声明播放进度能力的固件继续使用原协议。服务端仍记录打断和发送进度，但没有“确认播完”内容，也无法得出扬声器的精确断点。`tts.stop` 表示服务端结束发送，不能代替设备确认播完。

## 固件播放回执

WebSocket 或 MQTT+UDP 的活动语音会话，在 `hello.features` 中声明：

```json
{"type":"hello","features":{"playback_progress":true}}
```

声明后，本轮的 TTS 消息增加 `response_id`，每个 `sentence_start` 还增加从 `1` 开始递增的 `segment_id`。`session_id`、`response_id` 均使用服务端实际下发的值：

```json
{"type":"tts","state":"sentence_start","session_id":"session-1","response_id":"reply-1","segment_id":2,"text":"第二段讲解。"}
```

打断产生的 `tts.stop` 携带对应 `response_id` 和 `interrupted:true`，不能作为正常完成的依据。尚未进入模型回复的提示音或控制消息不保证包含回复编号。

设备在扬声器完整播完某段后报告连续播完的最大编号。收到或解码音频、显示字幕、写入播放队列不等于完整播完。按键打断时，先报告此前完整播完的段号，再按原协议发送 `abort`；被截断的半句不计入编号。尚无完整段落时填 `0`。

```json
{"type":"playback_progress","session_id":"session-1","response_id":"reply-1","state":"interrupted","played_through":1}
```

`state` 可取 `played`（进度）、`interrupted`（设备中断）、`finished`（本轮真正播完）。`finished` 只能在收到本轮 `tts.stop` 且播放缓冲排空后报告，`played_through` 必须等于最后一个段号。普通进度可逐段或合并报告，编号累计且不能回退；回执允许在打断后补报对应旧回复，不会改变新回复的状态。

服务端校验能力声明、当前会话、已知回复、整数段号、已成功发送及单调进度，忽略错误回执。旧回复的延迟字幕在出队时被丢弃，不得标记为新回复内容。协议通过原有 JSON 透传接入，不需要新接口或设备密钥。

段落粒度取决于 TTS Provider 实际发送的 `sentence_start`。若 Provider 整篇只发一个段落，回执也只能确认整段，不能精确到字符或毫秒。设备端需保留段号与实际播放队列的对应关系；本仓库没有固件实现，上述能力需固件团队接入后才会产生设备确认。

## 验证

`server/tests/test_playback.py` 覆盖真实 chat → TTS 消息 → abort → 下一轮模型请求，校验生成、开始发送和设备确认三种进度；另验证长回复不截断、迟到回调、回执隔离、乱序、失败发送、存储边界与配置校验。测试不代表实体扬声器已经支持播放回执。
